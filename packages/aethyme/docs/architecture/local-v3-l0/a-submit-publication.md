### Can candidate construction be separated from gating and from promotion?

- **Construction vs. gating: partly.** `build_submission_plan` (`:1398`) and `replay_submission_plan` (`:1252`) are pure functions of (session, head, base) that return a tree, and the read-only `Broker::submission_plan` (`:505`) already calls them without gating. But the candidate *commit* (`merge_commit`) is minted inside `simulate_and_gate_against`, interleaved with queue-status writes and slot acquisition. Extracting it means splitting `:975-1003` (commit_tree) from `:1005` onward.
- **Gating vs. promotion: yes.** `promote(entry_id)` (`:1749`) is a separate public method that consumes the recorded `{base, merge_commit}`. The auto-promote call at `:1225` is the only coupling.
- Both seams are internal (`fn`, `pub(crate)`). L4 #663 can wrap them as the "legacy Git adapter" without changing CLI contracts.

### What verify-only does end to end (this repository: `.aethyme/config.toml:27 mode = "verify-only"`)

1. `submit_inner` refreshes the disposable integration branch (`reconciliation.rs:809`, only in verify-only) and audits leases. `submission_base()` (`src/merge.rs:568`) picks **the fetched `origin/<default>`**, or falls back to integration and reports a `fallback_reason`.
2. Plan → replay → build the merge commit → gates on the merged tree, using the base's policy → the entry ends `Verified`, `Rejected`, `Conflict` or `Submitted+deferred`.
3. No promotion. `promotion_suppressed` explains why (`:1232-1243`). The integration ref is never advanced by submit.
4. Publication is **not** `ship`: `ship_plan_with_delivery_mode` refuses verify-only (`src/ship.rs:612-619`) and points to `broker push --session <id> --pr` (`src/session_push.rs`: pushes exactly the `agent/*` ref, gated by `[delivery] push_session_branches`, which is true here at `config.toml:297`).
5. Landing is proven afterwards by content (`representation.rs`), not by the queue.

- **Consequence for L4/L5:** in verify-only, each session is verified alone against `origin/main`. No combined candidate of several sessions is ever built or gated. Cross-session interaction is detected only as a textual conflict when the other session has already landed upstream.
- **Possible discrepancy (unverified impact):** the read-only `submit plan` CLI (`cli/submit.rs:495` → `Broker::submission_plan` → `integration_head_snapshot`, `merge.rs:2055`) plans against **integration**, while `submit` verifies against **upstream** in verify-only. These coincide only when integration was refreshed to upstream. Separately, the comment at `merge.rs:637` ("a verify-only plan is measured against integration") contradicts `submission_base`. Follow-up: a test for plan/submit base parity in verify-only.

## Reuse summary for downstream packages

- **L4 #663 (legacy adapter):** wrap `build_submission_plan` + `replay_submission_plan` + `promote` as-is. Extract the merge-commit minting from `simulate_and_gate_against` and give it a typed candidate record in place of `details_json`.
- **L4 #664/#665:** nothing existing composes more than one contribution or merges structurally. Inherited-commit skipping (ownership × integration state) is the only lineage logic.
- **L5 #666/#667:** promotion CAS plus recursive re-queue is the existing wave mechanism. Fairness, budgets and a single-controller identity are absent.
- **L6:** base-commit gate policy and the exact-tree verification slot are reusable. The gate cache key lacks environment identity (see the gates slice).
- **L7 #674/#675:** exact-SHA confirmation, plan digest, coordinated-operation journal, and the `PullRequestMerged` vs. `Published` distinction are reusable. Gaps: reconcile is operator-asserted; verify-only publishes through `session_push`, not `ship`; Mergify is unverified.
- **L8 #676:** reuse the claim/generation/backoff/dead-letter mechanics. The payload is PR-typed and duplicated between two outboxes.
